<domain>
## Phase Boundary

Phase 10 turns the already-delivered solo Pro loop into a guided adaptive program system.

The phase delivers **Programa Pro: Ciclo de Spray**: a 30-day Pro training cycle with four adaptive weeks, contextual missions, operational/technical/monthly checkpoints, recovery behavior, active-line continuation, dashboard command state, a dedicated program route, and entitlement-aware Free/Pro projection.

This phase organizes the existing evidence loop:

**Analisar -> Treinar -> Validar -> Evoluir**

- **Ciclo Pro organizes** the 30-day program, weekly rhythm, missions, checkpoints, recovery, and continuity.
- **Spray Lab executes** the guided training sessions already built in Phase 9.
- **Analyze validates** compatible clips through the existing browser-first analysis path.
- **History audits** program evidence, checkpoints, validation, repairs, and cycle outcomes.
- **Dashboard commands the now** with the current mission, state, blocker, and CTA.

This phase must not become a generic course product, a content library, a broad habit app, global ranking, team/coach workflow, social premium loop, or backend video-processing path. It must preserve browser-first analysis, evidence honesty, weak-evidence downgrade, compatible validation as technical proof, privacy-minimal data, server-owned entitlement truth, and no perfect-sensitivity/guaranteed-improvement claims.

<decisions>
## Implementation Decisions

### Program Shape And Rhythm
- **D-01:** The primary product experience is **Programa Pro: Ciclo de Spray**.
- **D-02:** User-facing perception is a premium 30-day program; operational execution is four adaptive weekly cycles.
- **D-03:** The short UI name is **Ciclo Pro**.
- **D-04:** Preferred CTAs and labels include `Abrir Ciclo Pro`, `Desbloqueie o Ciclo Pro de 30 dias`, `Semana 2 de 4`, and contextual history labels such as `Ciclo Pro Beryl 3x 50m`.
- **D-05:** Each 30-day Ciclo Pro has four adaptive weeks.
- **D-06:** Each week has five main missions plus two flexible slots.
- **D-07:** The weekly spine is: open the week, execute Spray Lab, adjust or repeat, record compatible validation, close checkpoint, then use two flexible slots for recovery, repair, validation, transfer, or buffer.
- **D-08:** Weak evidence must not produce fake progress. If evidence is weak, the week becomes repair or consolidation rather than pretending advancement.

### Ciclo Pro Birth, Repair Cycle, And Line Continuity
- **D-09:** A full Ciclo Pro can start only when there is a minimally usable base: saved analysis, recognizable context, and a protocol or active line.
- **D-10:** Weak base evidence creates **Ciclo de Reparo**, not a broken paywall or fake program.
- **D-11:** Ciclo de Reparo is a short premium cycle for cleaner capture, stable variables, context completion, and first compatible validation.
- **D-12:** Ciclo de Reparo is not punishment and not a low-quality teaser. It is the honest premium path when a full Ciclo Pro cannot yet be supported.
- **D-13:** A new Ciclo Pro starts after a completed monthly cycle with a clear next context or after a structural active-line restart.
- **D-14:** Structural line restarts happen only for meaningful changes such as weapon, optic/scope, sensitivity, DPI, FOV, relevant distance, patch, posture/setup, or critical loadout/attachment context.
- **D-15:** Old lines remain archived as audit history; they are not overwritten by the new cycle.

### Missions
- **D-16:** Missions are contextual microtasks, not generic tasks, XP chores, or course lessons.
- **D-17:** Every mission must have this premium anatomy: **Agora**, **Por que importa**, **O que invalida**, **Evidencia gerada**, and **Proximo CTA**.
- **D-18:** A mission must change a real program state: evidence improved, validation pending, blocker repaired, protocol stabilized, line continued, or cycle stepped back.
- **D-19:** Mission categories include execution, validation, repair, preparation, and transfer.
- **D-20:** Execution missions run or continue Spray Lab sessions attached to the current protocol/context.
- **D-21:** Validation missions guide compatible clip recording with preserved weapon, optic, distance/range, sensitivity, DPI, VSM/FOV, stance, attachment/loadout, patch, spray type, and relevant preparation variables.
- **D-22:** Repair missions address capture weakness, missing distance, changed variable, fatigue, confusion, low Spray Lab fidelity, outcome conflict, or inconclusive validation.
- **D-23:** Preparation missions are allowed only when they protect evidence quality or execution fidelity. They must not become a generic habits module.
- **D-24:** Transfer missions cover TDM/real-match practical transfer with conservative copy; they do not replace compatible clip validation as technical proof.
- **D-25:** Avoid missions such as generic `treine 20 minutos`, `melhore sua mira`, course lesson completion, empty XP, or any task without direct evidence/context connection.

### Checkpoints
- **D-26:** Checkpoints use three layers: operational weekly, technical validated, and monthly program.
- **D-27:** The operational weekly checkpoint always exists and closes the week with an honest state such as executed, stabilized, repair needed, inconclusive, variable changed, or repeat needed.
- **D-28:** The technical validated checkpoint exists only when compatible clip evidence is strong enough.
- **D-29:** Technical checkpoint outcomes include progress validated, regression validated, no clear change, incompatible context, or insufficient evidence.
- **D-30:** The monthly program checkpoint summarizes all four weeks by strict context: what consolidated, what remains pending, which active line continues, what blockers appeared, and which next Ciclo Pro or Ciclo de Reparo is recommended.
- **D-31:** Monthly checkpoint must not become a global player grade, rank claim, or final skill score.

### Adaptation, Reset, And Recovery
- **D-32:** The week can close by rhythm, but difficulty, phase, and coach aggressiveness can increase only when evidence converges.
- **D-33:** Evidence convergence should consider Spray Lab fidelity, outcomes, compatible validation, precision trend, blocker state, and conflict state.
- **D-34:** Coach aggressiveness is independent from calendar completion. Even if a week closes, the coach may maintain, reduce, or repair when evidence is weak/conflicting.
- **D-35:** Recovery uses a hierarchy: `reparar`, `consolidar`, and `reiniciar linha`.
- **D-36:** `reparar` applies to evidence/execution problems: weak clip, missing distance, low fidelity, fatigue, confusion, incomplete outcome, or inconclusive validation.
- **D-37:** `consolidar` applies when there is useful training but not enough proof to increase difficulty or claim progress.
- **D-38:** `reiniciar linha` applies only when structural context changed enough that the old line should not be mixed with the new one.
- **D-39:** Fatigue reduces dose, increases rest, shortens the session, and keeps context where possible.
- **D-40:** Pain, numbness, tingling, or significant discomfort stops the block. It is not counted as technical failure.
- **D-41:** Confusion simplifies the mission, reduces variables, and creates a clarity/recovery mission.
- **D-42:** Repeated failure returns the cycle to consolidation rather than increasing difficulty.
- **D-43:** Low fidelity creates repair before any strong validation request.
- **D-44:** User-facing language must never say the user failed. The product should frame recovery as preserving evidence and stabilizing execution.

### Missed Days And Inconsistent Use
- **D-45:** Missed days use premium evidence-based reentry, not punishment.
- **D-46:** A simple delay with no variable/context change repositions the mission and keeps the week alive.
- **D-47:** A variable break creates repair or line restart depending on severity.
- **D-48:** A stale context asks for a fresh analysis or short validation before increasing difficulty.
- **D-49:** A long absence can pause, freeze, or close the cycle with an honest state such as `concluido_sem_validacao`, but must not invent progress.
- **D-50:** Preferred copy posture: `o ciclo foi reencaixado para preservar evidencia`.

### Official Cycle States
- **D-51:** The official cycle/program states are: `preparando`, `ativo`, `reparando`, `consolidando`, `validacao_pendente`, `progresso_validado`, `sem_mudanca_clara`, `regressao_validada`, `inconclusivo`, `linha_reiniciada`, and `concluido`.
- **D-52:** Planning may add a paused/frozen/stale state only if needed for missed-day handling, but it must preserve the same evidence honesty.
- **D-53:** States must be stable technical values under the hood and polished pt-BR copy in UI.
- **D-54:** Program states must drive UI, persistence, coach handoff, dashboard CTA, history audit, and tests.

### Transparent Adaptation
- **D-55:** Every program change must have a short visible reason.
- **D-56:** Reason examples: fidelity dropped, validation inconclusive, variable changed, outcome conflicted with clip, fatigue reduced dose, context became stale, compatible proof missing, or blocker repaired.
- **D-57:** The program must not feel magical or opaque. It should feel like a serious coach explaining why the plan changed.
- **D-58:** Adaptation reasons should use stable reason codes plus concise user-facing copy.

### Free, Pro, Paywall, And Product Value
- **D-59:** Free remains premium and useful.
- **D-60:** Free can show the next recommended step, one honest basic weekly mission, blockers, evidence, and a clear CTA toward Ciclo Pro.
- **D-61:** Free must not use fake data, deceptive blur, or hide truth-contract evidence.
- **D-62:** Pro is where the full program exists: 30-day Ciclo Pro, four adaptive weeks, contextual missions, checkpoints, recovery, history, comparisons, audit, and active-line continuity.
- **D-63:** Paywall posture: `O Free te mostra o proximo passo. O Pro organiza sua evolucao em um ciclo completo, adaptativo e auditavel.`
- **D-64:** Program value must be sold as original Sens PUBG value: analysis, coach workflow, history, Spray Lab, validation, and adaptive program continuity.
- **D-65:** Do not monetize exclusive PUBG API-derived data or imply official PUBG/KRAFTON affiliation.
- **D-66:** Do not promise guaranteed improvement, perfect sensitivity, rank gain, final certainty, or global player grade.

### Dashboard, Program Route, And Surface Roles
- **D-67:** Dashboard is the cockpit of now.
- **D-68:** A dedicated program route is the full 30-day map of Ciclo Pro.
- **D-69:** Dashboard should show current week, dominant mission, program state, evidence, next CTA, and honest blocker.
- **D-70:** Program route should show the 30-day cycle, four adaptive weeks, missions by week, checkpoints, history, active line, repairs, comparison between weeks, and evidence audit.
- **D-71:** Dashboard must not become a large report. Program route must not be hidden behind a tiny card.
- **D-72:** History remains the audit/evolution surface for old cycles, checkpoints, validation, repairs, and line restarts.
- **D-73:** Analyze remains clip ingestion and validation; Phase 10 must not move video analysis into the program route.
- **D-74:** Spray Lab remains the runner/execution cockpit; Phase 10 must not rebuild the Spray Lab runner inside Ciclo Pro.

### Copy And Tone
- **D-75:** Use premium system language: Ciclo Pro, missao, linha ativa, checkpoint, validacao, reparo, consolidacao, reencaixe, contexto, evidencia.
- **D-76:** Avoid course/library/game language: aula, curso, XP, desafio generico, grind, lesson, guaranteed progress, rank promise.
- **D-77:** Copy should be pt-BR, concise, premium, serious, and honest.
- **D-78:** Repair and recovery copy must feel like coaching, not punishment.

### Verification And No False Done
- **D-79:** Phase 10 requires a dedicated verification gate, expected as `npm run verify:phase10:programs` or equivalent.
- **D-80:** Required matrix includes Free, Pro, no analysis, weak evidence, Ciclo de Reparo, active cycle, repair, consolidation, validation pending, progress validated, no clear change, regression validated, fatigue, pain/discomfort stop, variable changed, stale context, missed days, line restarted, completed cycle, and locked/upgrade states.
- **D-81:** Tests must cover program contract, cycle state transitions, mission anatomy, checkpoint layers, recovery/reentry rules, Free/Pro projection, dashboard cockpit, program route, history audit, Spray Lab handoff, Analyze validation handoff, copy safety, and no-overclaim behavior.
- **D-82:** Required gates include focused Phase 10 tests plus `npm run typecheck`, `npx vitest run`, `npm run benchmark:gate`, relevant Playwright/browser evidence, and `npm run build` when implementation touches routes or UI.
- **D-83:** If the dedicated program route, dashboard cockpit, Free/Pro projection, recovery states, or verification matrix are only partially implemented, final status cannot be `Delivered`.

### the agent's Discretion
The researcher/planner may choose exact route path, component names, schema/table names, field names, enum naming, query-param shape, visual layout, exact copy wording, state-machine implementation, and plan wave count.

That discretion does not include turning Ciclo Pro into a generic course, hiding evidence/blockers, weakening compatible validation, duplicating Spray Lab runner behavior, treating TDM/real-match transfer as technical proof, making Free feel broken, using fake locked data, storing sensitive health detail, making private clips train global models without consent, overclaiming guaranteed improvement, or marking the phase done without the dedicated Phase 10 program verification matrix.
